NicoStan is an R package that works for statistical models programmed in the
probabilistic programming language Stan.
For models with high-dimensional Gaussian latent variables/nuisance parameters,
NicoStan's algorithm uses standard HMC for the main model parameters,
and diffusion-pathspace HMC for the nuisance parameters.
Many statistical models require nuisance parameters, such as:
binary/ordinal multivariate probit models
(e.g., for econometrics and diagnostic test accuracy with imperfect gold standards),
and stochastic volatility (e.g., for quantitative finance, econometrics, medicine).
It also uses between-chain adaptation to achieve more efficient burnin/warmup,
as well as state-of-the-art burnin algorithms (e.g., ChEES-R-HMC, SNAPER-HMC).
NicoStan also offers rapid parallel estimation of posterior summaries,
and only monitors/stores the trace for the main model parameters (by default),
which - especially for large N - can greatly improve efficiency (time to min(ESS))
as well as lead to dramatic reductions in hard drive storage space.

What is NicoStan?

NicoStan is an R package for efficiently fitting Bayesian models written in the probabilistic programming language Stan.

NicoStan accesses Stan's log posterior and its gradient through BridgeStan (Roualdes et al., 2023); more specifically, NicoStan's C++ sampler calls the compiled Stan model directly through BridgeStan's C/C++ interface. NicoStan itself handles the burnin, the sampling and the posterior summaries.

NicoStan grew out of our work on efficient sampling for multivariate probit (MVP) models, specifically their latent class extensions (e.g., the LC-MVP), which are used for the evaluation of diagnostic/screening test accuracy without a perfect gold standard (see e.g., Xu et al., 2013; Xu and Craig, 2009; Uebersax, 1999; and Cerullo et al., 2025, Latent class multivariate probit and latent trait models for evaluating test accuracy without a gold standard: A simulation study).

Also, NicoStan is named after a cat, who provided great stress-relief whilst I was making NicoStan, and made waiting 10+ minutes for C++ code to recompile tolerable.

NicoStan was formerly called "BayesMVP" (since we have mainly been working with multivariate probit [MVP] models); however, it is now split into 3 R packages: NicoStan, the general Stan interface (which relies heavily on BridgeStan); NicoSIMD, which holds every AVX2 / AVX-512 function and is installed with NicoStan; and BayesMVP, which is now an extension to NicoStan, rather than a standalone R package.

The BayesMVP R package extension to NicoStan adds highly optimised, specialised implementations of these models, with manually implemented gradients (see the BayesMVP section below). For instance, we used BayesMVP to fit the models in our simulation study (Cerullo et al., 2025), which compared the LC-MVP and latent trait (Qu et al., 1996) models.

To summarise, the NicoStan R package provides:

  • A general Stan interface, so that existing Stan models can be fitted via NicoStan (directly, using the user's existing .stan model files).
  • nico_reduce_sum and nico_map_rect: NicoStan's versions of Stan's `reduce_sum` and map_rect, which move reduce_sum's bookkeeping inside the chunks; furthermore, the nuisance blocks are held by NicoStan inside the chunks, so that the main autodiff tape holds no node per nuisance value. NicoStan also chooses the number of threads per chain and the number of chunks, separately for the burnin and for the sampling, based on the tape-chunking method of "Cache-aware chunking dramatically improves parallel scaling for HMC: Application to multivariate probit model" (in preparation). See nico_reduce_sum and nico_map_rect for more information.

  • Hybrid diffusion-pathspace HMC for models with suitable Gaussian latent/nuisance blocks, based on Beskos et al., 2011, and Beskos et al., 2013. See Models with nuisance parameters.
  • Between-chain adaptation during burnin: all chains share the same step size ε, trajectory length τ and metric M; at each burnin iteration, the gradients which Adam (Kingma and Ba, 2015) uses to adapt ε and τ are averaged across the chains, and M is estimated from all of the chains, so that each burnin iteration gives as much information for the adaptation as N_chains iterations of one chain (Hoffman et al., 2021).
  • ChEES, ChEES-R and SNAPER-HMC trajectory-length adaptation during burnin, based on Hoffman et al., 2021, and Sountsov and Hoffman, 2022, as well as our blended criteria (geometric means of ESJD, ChEES-R and SNAPER). See Efficient burnin algorithms and Blended trajectory-length criteria for more information.
  • Custom AVX2 and AVX-512 maths functions, supplied by NicoSIMD (installed with NicoStan), and available to general Stan models (on 64-bit ARM CPUs, through SIMDe); however, note that your .stan model file will need to be re-written to declare the custom functions (e.g. vector nico_Phi(vector x);, with no body), and to replace standard Stan math functions (e.g. Phi()) with their nico_ counterparts (e.g. nico_Phi()), with NicoSIMD's C++ .hpp header file supplied when compiling (via Stan_cpp_user_header). See Custom AVX2 and AVX-512 functions.
  • Partially-dense metric: NicoStan allows you to set a dense HMC mass matrix (M) for the main model parameters (metric_shape_main = "dense"), combined with a diagonal M for the high-dimensional nuisance parameters. In other words, the main and nuisance metrics can be chosen separately. This is useful, because it is often intractable to fit a dense M on the entire parameter set, and a dense M for the main model parameters often leads to better sampling than a diagonal M, since it takes posterior correlations into account. Furthermore, users can set either an empirical M or a Hessian-based M (the Hessian computed by central differences of the gradient) for the main model parameters (metric_type_main = "Empirical" or "Hessian").

How is NicoStan different to Stan (e.g., cmdstanr/rstan)?

For the burnin (or "warmup") phase, Stan uses the No-U-Turn sampler (NUTS-HMC; see Hoffman and Gelman, 2014), which sets the HMC path length ($\tau$) automatically, within each chain.

On the other hand, NicoStan tunes $\tau$ with state-of-the-art, between-chain adaptation algorithms, such as SNAPER-HMC (Sountsov and Hoffman, 2022), ChEES-HMC (Hoffman et al., 2021) and ChEES-R-HMC (Sountsov and Hoffman, 2022), which is NicoStan's default (burnin_algorithm = "CHESSR").

NicoStan also offers geometric means of these criteria with the ESJD criterion (burnin_algorithm = "ESJD_CHESSR", "ESJD_SNAPER", "ESJD_CHESSR_SNAPER" and "ESJD_w50_CHESSR_w25_SNAPER_w25"). See this section below for more details on NicoStan's burnin algorithms.

This difference in burnin adaptation algorithm makes NicoStan more efficient than Stan for most models (see the Benchmarks section below).

In our testing, NicoStan can also perform very well with a very short burnin (100-125 iterations with just 4 chains; we are also currently testing shorter burnins).

Furthermore, since NicoStan uses between-chain adaptation (as opposed to within-chain adaptation, like Stan's NUTS-HMC algorithm), all chains finish the sampling phase at approximately the same time. This avoids the common issue of "stuck chains", which is often seen with complex models when using Stan directly (e.g., via cmdstanr or rstan).

Additionally, for models with high-dimensional nuisance parameters (see this section below for examples of such models), NicoStan offers a hybrid diffusion-pathspace HMC sampling algorithm (based on Beskos et al., 2011 and Beskos et al., 2013), which can greatly increase efficiency, especially for large N.

Furthermore, as we mentioned above (see this section), unlike Stan, NicoStan allows you to set a dense HMC mass matrix ($\mathbf{M}$) for the main model parameters (metric_shape_main = "dense"), combined with a diagonal $\mathbf{M}$ for the high-dimensional nuisance parameters (metric_shape_nuisance = "diag").

Note that NicoStan can also fit any Stan model (i.e., any .stan model file); however, expect efficiency gains (relative to Stan) to be less dramatic for models without high-dimensional nuisance parameters.

Installation

Warning: these R packages (NicoStan, NicoSIMD and BayesMVP) have not been tested on Windows in over 12 months, and have never been tested on macOS; almost all of the testing and development has been done on Linux (with x86 AMD CPUs). If you have any issues, please send an email to: enzo.cerullo@bath.edu.

NicoStan requires:

  • An R installation, a C++17 compiler (the build uses GCC's g++ with -std=gnu++17) and GNU make.
  • The cmdstanr R interface and the CmdStan C++ source tree. See the cmdstanr installation guide.
  • The BridgeStan R interface and its matching C++ source tree. See the BridgeStan installation guide.

NicoStan compiles against the Stan math library of your CmdStan source tree, including the copies of Eigen (3.4.0) and TBB that come with it.

The NicoSIMD package (the header-only C++ of the nico_ AVX2 / AVX-512 functions, with NEON on 64-bit ARM CPUs through SIMDe) is bundled with NicoStan; install_NicoStan() installs it first, before NicoStan itself, so it needs no separate installation.

The current development build uses CmdStan 2.36.0 and BridgeStan 2.6.2. NicoStan uses ~/.cmdstan/cmdstan-2.36.0 when that folder exists (otherwise the CmdStan path of cmdstanr), and the newest ~/.bridgestan/bridgestan-* folder.

We have tested NicoStan mostly on Linux, using R 4.3.3 and R 4.4.0 with GCC 11.4, with the C++ source trees at ~/.cmdstan/cmdstan-2.36.0 and ~/.bridgestan/bridgestan-2.6.2.

The compiler flags are set by the installer itself, for the CPU it is built on: -O3 -march=native -mtune=native, plus -mfma when the CPU has FMA, and then:

  • on a CPU with AVX-512: -mavx -mavx2 -mavx512f -mavx512cd -mavx512bw -mavx512dq -mavx512vl;
  • on a CPU with AVX2 (but not AVX-512): -mavx -mavx2;
  • on a 64-bit ARM CPU: -O3 -mcpu=native instead.

These can be overridden with the CUSTOM_FLAGS argument of install_NicoStan() (a named list; the accepted names include CXX_COMPILER, CXX_STD, CPU_BASE_FLAGS, FMA_FLAGS and AVX_FLAGS).

If you have any installation issues (e.g., C++ compiler errors) or bugs, please email me at: enzo.cerullo@bath.edu, or open an issue on GitHub.

Installation from local source files

If you have the NicoStan source files on your computer, source the administrator installer in inst/examples (`NicoStan_admin_install.R`):

source("path/to/NicoStan/inst/examples/NicoStan_admin_install.R")

The whole build runs in a clean R process, so that nothing is loaded or unloaded in your own R session.

Restart R after the installation, then load library(NicoStan).

The example source files are in inst/examples, and the installation copies them into the compiled package (after installation, they are in the folder given by system.file("examples", package = "NicoStan")).

Installation from GitHub

For installation from GitHub, start with a fresh R session and a writable package library, and install remotes (or devtools) first:

install.packages("remotes")
remotes::install_github(repo = "CerulloE1996/NicoStan",
                        upgrade = "never")
NicoStan::install_NicoStan()

Restart R, then load library(NicoStan).

Note that remotes::install_github() installs the outer R package and its installer; install_NicoStan() then installs NicoSIMD and compiles and installs the sampler itself.

Also, make sure to restart R before switching between the installed and development copies.

Installing the BayesMVP extension

The native (manually differentiated) multivariate probit and ordinal probit models and their examples additionally require the NicoStan-compatible BayesMVP extension. (The nico_ AVX functions themselves come from NicoSIMD, which is installed with NicoStan.)

After installing NicoStan, run the following in a fresh R session:

remotes::install_github(repo = "CerulloE1996/BayesMVP",
                        ref = "main",
                        upgrade = "never")
BayesMVP::install_BayesMVP()

Restart R before loading the compiled BayesMVP package.

install_BayesMVP() stops if NicoStan (version 0.1.9000 or later) is not installed.

Note that this command installs the main branch of BayesMVP.

Compatibility across devices

Warning: these R packages (NicoStan, NicoSIMD and BayesMVP) have not been tested on Windows in over 12 months, and have never been tested on macOS; almost all of the testing and development has been done on Linux (with x86-64 AMD CPUs). If you have any issues, please send an email to: enzo.cerullo@bath.edu.

This section applies to all three packages:

  • NicoStan (the sampler): written to compile on any 64-bit CPU with a C++17 compiler (i.e., x86-64 and 64-bit ARM CPUs, on Linux, Windows and macOS).
  • NicoSIMD (the SIMD functions, installed with NicoStan): which SIMD functions are used is decided when the model is compiled, from the instruction sets the compiler is told to use (-march=native on x86-64, -mcpu=native on 64-bit ARM), not whilst the model runs: the AVX-512 functions (8 doubles per operation) when the model is compiled with AVX-512F, AVX-512VL and AVX-512DQ; otherwise the AVX2 functions (4 doubles per operation) when it is compiled with AVX2; on a 64-bit ARM CPU the same AVX2 functions, translated into NEON instructions by SIMDe (each 256-bit AVX2 operation becomes two 128-bit NEON operations); on any other CPU, no SIMD functions, and the model runs on Stan::math (see NicoSIMD: the SIMD functions on every device).

Examples

The general examples are grouped by their parameterisation:

  • Hybrid/joint HMC with nuisance diffusion: Cox shared frailty, hierarchical logistic regression, joint longitudinal-survival modelling, a discrete-time AR(1) stochastic-volatility model (EASY_Stochastic_volatility.stan) and a latent-diffusion survival model (its nuisance block: standard normal Brownian increments). Continuous-time SV can introduce the additional path-discretisation difficulties described below.
  • Standard HMC: Weibull survival regression, robust Student-t regression and marginal Gaussian process (GP) regression (the latent GP integrated out, so these three models have no nuisance block).

The logistic random-intercept example gives a short introduction to the API:

source(system.file("examples", "random_intercepts.R", package = "NicoStan"))
fit <-  run_random_intercepts(burnin_algorithm = "CHESSR")
diagnostics <-  fit$summary(save_log_lik_trace = FALSE)
fit$model_fit_object$summaries$summary_tibbles$summary_tibble_main_params

## Other trajectory-length adaptation options (burnin_algorithm), e.g.:
## "SNAPER", "ChEES", "ESJD_CHESSR", "ESJD_CHESSR_SNAPER", "ESJD_w50_CHESSR_w25_SNAPER_w25"

The trajectory-length criteria that burnin_algorithm accepts (the default is "CHESSR", i.e., ChEES-R; the names are not case-sensitive, e.g., "CHEESR" is also accepted):

  • "CHESSR" (the default): ChEES-R, the ChEES criterion (Hoffman et al., 2021) per unit trajectory length (see Efficient burnin algorithms (SNAPER-HMC and ChEES-R-HMC)).
  • "ChEES": the original ChEES criterion (Hoffman et al., 2021).
  • "CHESSR_log": a smoothed log-rate variant of ChEES-R.
  • "SNAPER": the SNAPER criterion (Sountsov and Hoffman, 2022).
  • "CHESSR_time" and "SNAPER_time": the time-to-target-ESS variants of ChEES-R and SNAPER (joint sampler only; settings in time_criterion_settings).
  • "ESJD": the expected squared jumped distance (Pasarica and Gelman, 2010) per unit trajectory length.
  • "ESJD_CHESSR": the equally weighted geometric mean of the ESJD and ChEES-R criteria.
  • "ESJD_SNAPER": the equally weighted geometric mean of the ESJD and SNAPER criteria.
  • "ESJD_CHESSR_SNAPER": the equally weighted geometric mean of the ESJD, ChEES-R and SNAPER criteria.
  • "ESJD_w50_CHESSR_w25_SNAPER_w25": the same, with the weights 0.50, 0.25 and 0.25.

The four blended criteria are described in Blended trajectory-length criteria.

The summary tibbles report, for each parameter, the posterior mean, SD and quantiles, the bulk and tail ESS (n_eff and n_eff_tail; Vehtari et al., 2021), the ESS of the centred squared draws (n_eff_sd, i.e., the ESS for estimating the posterior SD), and the R-hat and nested R-hat (Margossian et al., 2024) convergence diagnostics (Rhat and n_Rhat).

This example simulates data with 20 groups and 200 observations, with a standard normal latent vector (i.e., the non-centred random intercepts) as the nuisance block, named with nuisance_params = "z". See the complete R example and Stan model for the full parameterisation and settings. Note that the R6 class is called NicoStan::Nico_model (NicoStan::MVP_model also still works, for compatibility reasons); Model_type = "Stan" must be selected when using a .stan model file; the other Model_type options require the BayesMVP R package extension to be installed (see BayesMVP: multivariate probit models).

The wider comparison examples are available through:

  • Use engine = "cmdstanr" for Stan's NUTS (Hoffman and Gelman, 2014), through cmdstanr.
  • Use engine = "NicoStan", math_backend = "Stan" for NicoStan with Stan::math.

The "AVX2" and "AVX512" options select the prepared AVX versions of the supplied example models (the *_avx.stan files); they require the BayesMVP extension and a CPU supporting the selected instruction set. For your own .stan model, either call the nico_ functions in the model yourself and supply their C++ header, or let NicoStan write the AVX version with Stan_model_math_functions in Nico_model$new() (see Custom AVX2 and AVX-512 functions).

Preparing your own Stan model

When preparing a model for NicoStan:

  • Name every nuisance block with nuisance_params = c(...) in Nico_model$new(), in any order (e.g., nuisance_params = c("z_intercept", "z_slope")); the blocks can be declared anywhere in the parameters block. NicoStan never chooses the nuisance blocks itself: with sample_nuisance = TRUE and no nuisance_params, it stops with an error saying so.
  • Set sample_nuisance = TRUE (or FALSE for a model without a nuisance block, i.e., every parameter is main).
  • Note that NicoStan then writes a version of the model, in the file NicoStan writes next to the model, whose nuisance blocks are held by NicoStan rather than declared as Stan parameters (each declaration is kept as a comment, and the model reads the values where it uses them).
  • For the nuisance blocks to be held by NicoStan inside the chunks, the model's reduce_sum (or reduce_sum_static) must slice the nuisance block; any other use of a block reads its values on the main tape (see Example 2 and nico_reduce_sum and nico_map_rect).

Worked examples

The files of Examples 1, 3 and 4 are in NicoStan's inst/examples folder (i.e., system.file("examples", package = "NicoStan") once NicoStan is installed): each has its Stan model and an R script which simulates or loads the data and fits the model. Example 2 is a sketch in the text only, with no file of its own.

Example 1: one nuisance block (logistic regression with random intercepts)

The nuisance parameters (here, the standardised random intercepts z) are named with nuisance_params = "z". With diffusion_HMC = TRUE and partitioned_HMC = FALSE, NicoStan samples the main and the nuisance parameters jointly, within the same trajectory and with one Metropolis-Hastings step: the nuisance block moves with diffusion-pathspace dynamics (Beskos et al., 2013) and the main parameters with standard HMC dynamics, with the kick-flow-kick integrator of Beskos et al., 2015.

Note that NicoStan never chooses the nuisance blocks itself: with sample_nuisance = TRUE they are always named, wherever they are declared in the parameters block, and a Stan model with sample_nuisance = TRUE and no named block stops with an error saying so.

The Stan model (random_intercepts.stan) is:

data {
  int<lower=1> N;
  int<lower=1> J;
  array[N] int<lower=1, upper=J> group;
  vector[N] x;
  array[N] int<lower=0, upper=1> y;
}
parameters {
  vector[J] z;
  real alpha;
  real beta;
  real<lower=0> sigma;
}
transformed parameters {
  vector[J] group_effect = sigma * z;
}
model {
  z ~ std_normal();
  alpha ~ normal(0, 1.5);
  beta ~ normal(0, 1);
  sigma ~ normal(0, 1);
  y ~ bernoulli_logit(alpha + beta * x + group_effect[group]);
}
generated quantities {
  real mean_probability = mean(inv_logit(alpha + beta * x + group_effect[group]));
}

Here z (one value per group, $J = 20$) is the nuisance block, and alpha, beta and sigma are the main parameters; group_effect = sigma * z are the non-centred random intercepts.

It is fitted as in random_intercepts.R, which gives every sampler setting explicitly. The model is first copied into a writable temporary folder, because NicoStan writes its version of the model (and BridgeStan compiles it) next to the model file, which cannot be done inside the installed package:

dir.create(path = model_directory)
model_file <-  file.path(model_directory, "random_intercepts.stan")
stopifnot(file.copy(from = system.file("examples", "random_intercepts.stan", package = "NicoStan"),
                    to = model_file))

Example 2: several nuisance blocks (nuisance_params)

A model may have any number of nuisance blocks, declared anywhere in the parameters block; they are given by name with nuisance_params, e.g., for random intercepts and random slopes (with the data block of Example 1):

parameters {
  real alpha;
  real beta;
  real<lower=0> sigma_intercept;
  real<lower=0> sigma_slope;
  vector[J] z_intercept;        // nuisance block 1
  vector[J] z_slope;            // nuisance block 2
}
model {
  z_intercept ~ std_normal();
  z_slope ~ std_normal();
  alpha ~ normal(0, 1.5);
  beta ~ normal(0, 1);
  sigma_intercept ~ normal(0, 1);
  sigma_slope ~ normal(0, 1);
  y ~ bernoulli_logit(alpha + sigma_intercept * z_intercept[group]
                      + (beta + sigma_slope * z_slope[group]) .* x);
}
model <-  NicoStan::Nico_model$new(Model_type = "Stan",
                                    Stan_data_list = stan_data,
                                    Stan_model_file_path = "random_intercepts_and_slopes.stan",
                                    nuisance_params = c("z_intercept", "z_slope"),
                                    sample_nuisance = TRUE)

Note that the nuisance blocks of nuisance_params are sampled by NicoStan, so sample_nuisance must be TRUE.

The initial values of each block are given by name, in its own shape (e.g., z_intercept = rep(0, J); for an array[E] vector[K] block, a matrix with one row per term, $E \times K$, or a list of its $E$ vectors); the initial values of a constrained block are given on its own, constrained scale, as for Stan; a block left out of the initial values starts at 0 on its unconstrained scale. Example 3 shows every step of a full fit (the priors, the nuisance blocks, the initial values, the optimal layouts and the summaries).

With nuisance_params, NicoStan writes its nico_reduce_sum version of the model (and its C++ user header) next to the model file. In it, the nuisance blocks are held by NicoStan, rather than declared as Stan parameters (the blocks one after the other, each in Stan's own order of its values), and every use of a block reads NicoStan's values where it is used; the rest of the model's code is kept as it is. When the model uses reduce_sum, a nuisance block which is its sliced argument is then held by NicoStan inside the chunks (see nico_reduce_sum for what this gives). Note that:

  • How many blocks: any number (each one named in nuisance_params).
  • Which shapes: vector[E], row_vector[E], array[E] real, array[E] vector[K], array[E] row_vector[K], matrix[R, C] and array[A] matrix[R, C] blocks, and tuples of these (see below).
  • Constraints: each of these may have the constraint <lower = a>, <upper = b>, <lower = a, upper = b>, <offset = a>, <multiplier = b> or <offset = a, multiplier = b>, whose bounds do not use a nuisance block: NicoStan then holds the block's unconstrained values, as Stan's own sampler does, every value the model reads is constrained with Stan math's own transform, and the log-Jacobian of the transform is added to the target. Any other block (e.g., an array of tuples, or an array of more dimensions) stops with an error saying so.
  • Slicing: Stan's reduce_sum slices arrays only, so a nuisance block which is the sliced argument of reduce_sum must be an array (e.g., array[N] real, array[N] vector[K] or array[N] row_vector[K]).
  • Tuples: a nuisance block may also be a tuple, so that blocks of different containers can be declared (and named in nuisance_params) at once, e.g.:
parameters {
  real alpha;
  real beta;
  real<lower=0> sigma_intercept;
  real<lower=0> sigma_slope;
  tuple(vector[J], vector[J]) z;   // z.1: random intercepts, z.2: random slopes
}
model {
  z.1 ~ std_normal();
  z.2 ~ std_normal();
  ...
}

with nuisance_params = c("z"). Each component of the tuple (including those of any tuple inside it) is then held as a nuisance block of its own, in the tuple's own order (which is also Stan's order of its values); its initial values are given as the tuple, by its name, as a list with one element per component. Note that an array of tuples (e.g., array[N] tuple(real, vector[K])) is not supported; declare it as a tuple of arrays instead (e.g., tuple(array[N] real, array[N] vector[K])).

Example 3: the multivariate ordered probit model with the fused GHK function (and BayesMVP)

The multivariate ordered probit (MVOP) model - i.e., a truncated multivariate normal for each subject, whose truncation region is set by the subject's binary and ordinal results - can be written in Stan with one of NicoSIMD's fused functions, nico_finite_mixture_of_multivariate_ordered_probit_GHK_log_likelihood, which computes the GHK log likelihood of a chunk of subjects, and its gradient, in one autodiff node.

It runs on any CPU with AVX-512 or AVX2, and on 64-bit ARM CPUs (e.g., Apple Silicon Macs), where NicoSIMD's functions run with NEON instructions (through SIMDe). On any other CPU, NicoSIMD gives no user header, so a Stan model that calls the function cannot be built there.

The same function also takes 2 or 4 latent classes (i.e., the LC-MVP and the LC-MVOP), binary, ordinal and mixed outcomes, each outcome's own covariates, missing results (coded -1, handled by the GHK method) and interval-censored ordinal results.

This example fits a one-class MVOP to the real NHANES data (the 9575 people of the NHANES data in the hexbin R package), with four outcomes, each with its own covariates: iron deficiency, low albumin and cancer (binary), and anaemia (ordinal: the WHO categories of haemoglobin for each sex, i.e., none / mild / moderate / severe).

The function is declared in the functions block without a body, and the nuisance block u_raw (one GHK value for each subject and outcome) is the sliced argument of `reduce_sum_static`, so that everything whose size grows with N is inside the chunks.

The priors are those of BayesMVP's MVOP model: normal priors on the coefficients, an LKJ prior on the correlation matrix and an induced Dirichlet prior on the cutpoints of each ordinal outcome.

The key parts of the Stan model (inst/examples/models/one_class_MVOP_with_the_fused_GHK_log_likelihood.stan) are:

functions {
      ////
      //// ---- NicoSIMD's fused GHK log likelihood, declared without a body (its 20 arguments: the full file)
      ////
      real nico_finite_mixture_of_multivariate_ordered_probit_GHK_log_likelihood( ... );
      ////
      //// ---- the partial sum of reduce_sum_static: the log likelihood of the subjects start, ..., end
      ////
      real partial_sum_of_the_GHK_log_likelihood_lpdf( array[] row_vector u_raw_slice, int start, int end,
                                                       ... ) {
            matrix[end - start + 1, 1] log_class_probability = rep_matrix(0.0, end - start + 1, 1);
            return nico_finite_mixture_of_multivariate_ordered_probit_GHK_log_likelihood(
                         u_raw_slice, 1, intercept, coefficients, set_of_class_and_test,
                         covariates[:, :, start:end], n_covariates, cutpoints, set_of_class_and_test,
                         position_of_first_cutpoint_of_test, L_Omega, log_class_probability,
                         y[start:end], y[start:end], test_is_binary, n_categories_of_test, test_at_GHK_position,
                         Phi_type, overflow_threshold, underflow_threshold);
      }
}
parameters {
      array[N] row_vector[n_tests] u_raw;     //// the nuisance block (given with nuisance_params)
      vector[n_coefficients_total] beta_vec;  //// the coefficients of each outcome (its intercept first)
      cholesky_factor_corr[n_tests] L_Omega;
      vector<lower=C_raw_lower, upper=C_raw_upper>[n_cutpoints_total] C_raw;   //// first cutpoint, then log gaps
}
model {
      ...   //// the priors, including the induced Dirichlet prior on the cutpoints
      target += reduce_sum_static( partial_sum_of_the_GHK_log_likelihood_lpdf, u_raw, chunk_size, ... );
}
generated quantities {
      matrix[n_tests, n_tests] Omega = multiply_lower_tri_self_transpose(L_Omega);
}

NicoSIMD gives the user header and the build arguments for the CPU in use, so that the same R code runs on every device.

Example 4: network meta-analysis of test accuracy with multiple thresholds (MetaOrdDTA's Xu model)

MetaOrdDTA's network meta-analysis (NMA) model of diagnostic test accuracy, i.e., the NMA model of Nyaga et al. (ANOVA model for network meta-analysis of diagnostic test accuracy data) with the fixed cutpoints of Xu et al. (Evaluating accuracy of diagnostic tests with intermediate results in the absence of a gold standard), is a Stan model which NicoStan fits unchanged. The model and MetaOrdDTA are described in Ordinal regression for meta-analysis of test accuracy: a flexible approach for utilising all threshold data. In this model, each test has one set of cutpoints per disease class, shared by every study.

Each study reports, for each of its tests, the number of non-diseased and of diseased patients above each of the test's thresholds. The thresholds a study did not report are coded -1: these are the "missing thresholds" the model is made for.

This example fits the model to simulated data: 4 ordinal anxiety screening tests (GAD-2, GAD-7, HADS and BAI) in 80 studies, each study with 1 to 3 of the tests (136 study-test pairs in all). The data were simulated with MetaOrdDTA's own simulator (R_fn_sim_NMA_data_with_covariates_varying()), with a design (which tests each study has, and the proportion of missing thresholds of each test) taken from a real NMA.

MetaOrdDTA prepares the data and the priors exactly as it gives them to Stan (MetaOrd_model$new(..., compile = FALSE): nothing is compiled or fitted by MetaOrdDTA here). NicoStan then fits MetaOrdDTA's Stan model, DTA_NMA_Nyaga_Xu_FIXEDthr.stan (on GitHub), with its #include files from MetaOrdDTA's stan_functions folder. The full R script, inst/examples/Run_network_meta_analysis_of_test_accuracy_Xu_fixed_cutpoints_with_MetaOrdDTA_and_NicoStan.R, reads the data and then fits the model in five steps: (a) the priors; (b) the nuisance parameters; (c) the initial values; (d) the layouts; and (e) the fit and its summaries.

BayesMVP: multivariate probit models

The BayesMVP R package extension to NicoStan provides specialised implementations, with manually derived likelihood gradients hand-coded in C++, of some particularly difficult-to-sample models; more specifically, it provides the following models:

  • MVP: multivariate probit, using Model_type = "MVP".
  • 2LC-MVP: 2-class multivariate probit, using Model_type = "LC_MVP".
  • MVOP: multivariate ordinal probit (which also supports mixed binary and ordinal outcomes), using Model_type = "MVOP".
  • 2LC-MVOP: 2-class multivariate ordinal probit, using Model_type = "LC_MVOP".
  • Latent trait: the 2-class implementation, using Model_type = "latent_trait".

These models handle correlated binary and/or ordinal outcomes, and their latent class extensions (LC-MVP, LC-MVOP) allow diagnostic/screening test accuracy to be estimated when a perfect reference/gold standard is unavailable.

The correlation matrices use the flexible Cholesky parameterisation of Sean Pinkney (Pinkney, 2024), which also allows the correlations to be constrained to be positive (corr_force_positive = TRUE), as well as custom element-specific bounds (via the lb_corr and ub_corr arguments, with one matrix per latent class).

Furthermore, any of the correlations can be fixed to known values, via the known_values_indicator_list argument (which indicates which correlations are known) and the known_values_list argument (their values).

Chunks and within-chain threads. BayesMVP's models work through the subjects in chunks: the forward pass and the (manual) gradients of each chunk are finished before the next chunk starts, in one workspace which is reused for every chunk (one workspace per thread, with within-chain parallelisation, i.e., WCP), so that, with the number of chunks chosen as below, each chunk's buffers stay in the CPU's L2 cache.

Similarly to the Stan models, the number of chunks and of within-chain threads of the burn-in and of the sampling are found by BayesMVP itself, from the L2 and L3 caches of the computer, followed by a short timed check of the layouts around them (BayesMVP::fn_compute_burnin_n_threads_WCP_and_num_chunks_for_BayesMVP_model() and BayesMVP::fn_compute_sampling_n_chains_n_threads_WCP_and_num_chunks_for_BayesMVP_model(), see Example 3), or by $sample() when they are left out.

The log density and its gradient do not depend on the number of chunks: in the evaluation the sampler uses, the largest relative difference from one chunk was 1.1e-14 (LC-MVP and LC-MVOP, with and without missing results, with nico::math (AVX-512) and with Stan::math, at 2 to 64 chunks against 1 chunk; the check is inst/BayesMVP/tests/check_that_the_BayesMVP_manual_gradient_models_give_the_same_log_density_and_gradient_at_every_number_of_chunks.R in BayesMVP).

The ordinal latent class model is described in Meta-analysis of dichotomous and ordinal tests with an imperfect gold standard (Cerullo et al., 2022). Furthermore, in Latent class multivariate probit and latent trait models for evaluating test accuracy without a gold standard: A simulation study (Cerullo et al., 2025), we compared the LC-MVP and latent trait models in a comprehensive simulation study, in which the models were fitted using BayesMVP.

Automatic test (column) reordering

For the latent class models (LC-MVP and LC-MVOP), BayesMVP chooses the order of the tests (i.e., the columns of y) automatically, before the main burn-in (reorder_cols_MVP = TRUE by default; reorder_cols_MVP = FALSE keeps the original order). The same is done, by default, for a Stan model whose data has a latent_test_order field (e.g. the four-class LC-MVOP).

The model itself does not depend on the order of the tests; however, the unconstrained parameters which HMC samples do - and hence so does the efficiency of HMC.

  • A short pre-burn-in gives rough estimates of the correlations, intercepts and (for ordinal tests) cutpoints; the most nearly deterministic test is then placed last, and the other tests follow the greedy correlation order (the most strongly correlated tests first).
  • This is because, in the GHK construction, each test's truncation bounds depend on the tests placed before it, and a nearly deterministic test has steep tail values which would otherwise propagate to every later test; the order also sets the order of the correlation parameterisation (Pinkney, 2024).
  • The rule can be chosen with test_order_rule_for_reorder_cols_MVP; e.g. the old greedy-only rule is test_order_rule_for_reorder_cols_MVP = "greedy_correlation_order".
  • On our binary LC-MVP model (N = 10,000), the slower order of the old greedy-only rule needed 1.60x the gradient evaluations to reach the target min ESS (0.59x the min ESS per 1000 gradient evaluations); on our ordinal LC-MVOP model (N = 5,000), placing the binary test last needed 0.67-0.75x the gradient evaluations of the input order.
  • The summaries and traces are returned in the original test order.

See the BayesMVP README for more details.

Benchmarks

In our initial tests, NicoStan, combined with the BayesMVP extension, was over 150x faster than Stan, and around 50x more efficient than Mplus. These numbers are for the latent class multivariate probit model (LC-MVP), using an N = 10,000 simulated binary dataset with 6 binary tests in total (hence a total of 60,000 observations), which is based on real, publicly available COVID-19 data. These models (LC-MVP) are used in both human and veterinary medicine for estimating diagnostic and screening test accuracy without a perfect gold standard.

For our ordinal example dataset (using the LC-MVOP model), which is based on a real dataset on three tests to screen for and/or diagnose depression (more specifically, the MINI as the imperfect gold standard, and the PHQ-9 and CES-D-10 as the two ordinal tests), for N = 5,000 (hence 15,000 observations in total, since there are 3 tests), we found that NicoStan with BayesMVP (using the LC-MVOP model) was over 50x more efficient than Stan and over 1000x more efficient than Mplus. The latter is because, despite being very efficient for the binary LC-MVP, the Gibbs-based algorithm of Mplus struggles greatly with ordinal outcomes, and Mplus does not let you fit ordinal outcomes with more than 10 categories; hence, we had to group categories together just to attempt to measure its efficiency. Note that this is not ideal: we would never recommend grouping categories in real-life data analysis, nor would we suggest assuming continuity just because there are a lot of categories (especially for single studies and for latent class models).

Furthermore, even when using NicoStan without BayesMVP (i.e., using the .stan model file directly, without the hand-coded C++ gradients and the AVX functions), we still found that NicoStan was over 10x more efficient than Stan (via cmdstanr), for both the LC-MVP and the LC-MVOP examples described above. These fits use Stan::math (i.e., Stan's own C++ maths library), so the gains come from the sampler and its burn-in adaptation. The nico::math (AVX) versions, i.e., the same models with the AVX2 / AVX-512 nico_ functions of NicoSIMD (which BayesMVP uses), give a further route to speeding things up.

More detailed and comprehensive benchmarks are coming soon. The comparisons will cover:

  • Stan (NUTS, via cmdstanr), fitted using the default NUTS-HMC algorithm (Hoffman and Gelman, 2014).
  • NicoStan, using the same Stan model with Stan::math.
  • NicoStan, using the same Stan model with nico::math (AVX2 and/or AVX-512, on CPUs that support them).

All of these comparisons use the same data, priors and initial values. The results will report sampling efficiency in terms of effective sample size (ESS); more specifically: (i) sampling ESS/sec; (ii) the time taken to reach a minimum ESS of 100, 1,000 and 10,000; and (iii) sampling ESS per gradient evaluation (ESS/grad). Additionally, we will report the warm-up (Stan) and burn-in (NicoStan) costs, as well as convergence diagnostics (e.g., R-hat and nested R-hat [nR-hat]; Margossian et al., 2024), alongside the computational settings.

Trajectory-length criteria within NicoStan

We also compared NicoStan's trajectory-length criteria (the burnin_algorithm option strings in brackets): ChEES (Hoffman et al., 2021; "ChEES"), ChEES-R (NicoStan's default; "CHESSR"), SNAPER (Sountsov and Hoffman, 2022; "SNAPER"), the ESJD rate (Pasarica and Gelman, 2010; "ESJD"), and the two blends that we proposed: ESJD x ChEES-R = sqrt(C_ESJD * C_ChEESR) ("ESJD_CHESSR") and ESJD x SNAPER = sqrt(C_ESJD * C_SNAPER) ("ESJD_SNAPER").

Maximising a geometric mean is the same as maximising the average of the logarithms of the criteria; in other words, each criterion contributes equally to the choice of the trajectory length (tau), whatever its scale.

"Cells OK" counts the cells in which the criterion was the best, or within noise of the best with the 95% interval of its seed-matched ratio within plus or minus 25%. Models with nuisance parameters (diffusion-pathspace HMC)

NicoStan is particularly aimed at models with a large block of latent / nuisance parameters for which analytic marginalisation is unavailable, or numerical marginalisation is too expensive.

Techniques such as non-centring can improve the posterior geometry of some of these models; however, they do not remove the nuisance block: the latent variables still have to be sampled.

Such blocks occur in many commonly used models, e.g.:

  • MVP, LC-MVP, MVOP and LC-MVOP: latent Gaussian / auxiliary variables for correlated binary and / or ordinal outcomes. The augmented state grows with the number of individuals and outcomes; evaluating the marginal likelihood instead involves multivariate Gaussian rectangle probabilities.
  • Generalised linear mixed models: Gaussian random intercepts / slopes for binary, ordinal or count outcomes, particularly when there are many subjects / groups or crossed random effects.
  • Generalised additive mixed models: Gaussian spline coefficients and random effects, with non-Gaussian observations leaving a non-conjugate posterior over those coefficients.
  • Gaussian processes with non-Gaussian likelihoods: latent function values for binary, ordinal or count outcomes.
  • Spatial and spatio-temporal models: Gaussian spatial fields, temporal effects and their interactions, e.g. in binomial / Poisson disease-mapping models.
  • Log-Gaussian Cox processes: a Gaussian latent log-intensity field, often represented on a large spatial mesh / grid.
  • Stochastic volatility: a latent log-volatility path in discrete-time models, or a latent volatility diffusion in continuous time. E.g., path augmentation for a partially observed volatility diffusion introduces latent points between the observations; the discretisation then controls both the approximation error and the size of the sampled path (see Beskos et al., 2013). The discrete-time AR(1) version has a simpler time structure, but neither the centred nor the non-centred parameterisation is uniformly efficient across all regimes (Kastner and Frühwirth-Schnatter, 2014).
  • Non-linear / non-Gaussian state-space models and partially observed diffusions: latent states, state innovations or a non-centred driving path.
  • Survival models with log-normal frailty: Gaussian log-frailties at the individual / cluster level, with the hazard / survival likelihood generally preventing analytic integration.
  • Joint longitudinal and survival models: shared random effects or latent biomarker trajectories; the survival component generally prevents the Gaussian marginalisation available for simpler longitudinal models.
  • Item-response and non-Gaussian factor models: latent abilities / factors for binary, ordinal or count responses.
  • Non-linear mixed-effects models: Gaussian individual-level effects entering a non-linear response model, e.g. in population pharmacokinetic / pharmacodynamic (PK/PD) models.
  • Measurement-error models with non-linear / non-Gaussian outcomes: unobserved true exposures / covariates or residual processes that enter the outcome likelihood.
  • Non-linear inverse problems with Gaussian-prior fields: unknown spatial functions or initial conditions, e.g. log-permeability fields inferred through a groundwater-flow model.

For examples of these structures, see the Stan item-response models, the non-linear mixed-effects PK models of Johnston et al., 2024, the diffusion bridge, stochastic volatility and latent diffusion survival applications of Beskos et al., 2013, and the function-space applications of Cotter et al., 2013.

The runnable examples show the implementations currently supplied with NicoStan. Note that the supplied discrete-time AR(1) stochastic volatility example is a different model from the continuous-time experiments of Beskos et al., 2013 and Beskos et al., 2015.

Note that some simpler Gaussian models allow the latent block to be integrated out analytically. E.g., our Gaussian-outcome GP regression example uses the marginal likelihood and is fitted with standard HMC; the latent-GP examples listed here instead have non-Gaussian likelihoods.

How NicoStan samples the nuisance block: diffusion-pathspace HMC and hybrid HMC

Many models have a relatively small number of main parameters, $\boldsymbol{\theta}$, and a much larger block of nuisance parameters, $\mathbf{u}$, whose (non-centred) prior is standard normal, i.e. $\mathbf{u} \sim \text{multi\_normal}(\mathbf{0}, \mathbf{I})$.

As the number of nuisance parameters, $D_{\text{nuisance}}$, grows, standard HMC needs an increasingly small step size, of order $D_{\text{nuisance}}^{-1/4}$, to keep its acceptance rate (see Beskos et al., 2013, section 3.3, and the references therein).

Diffusion-pathspace HMC (Beskos et al., 2011; Beskos et al., 2013) avoids this by integrating the Gaussian part of the Hamiltonian dynamics exactly: the potential of $\mathbf{u}$ is written as $\frac{1}{2} \mathbf{u}' \mathbf{u} + \Phi(\mathbf{u})$, and each step is a "kick" (which updates only the momentum, using the gradient of $\Phi$), an exact "rotation" of the Gaussian part, and a second kick.

Since the rotation leaves the Gaussian reference measure invariant, the integration error only comes from $\Phi$; hence, under the conditions given by Beskos et al., the step size does not need to decrease as $D_{\text{nuisance}}$ grows.

NicoStan samples the main parameters and the nuisance parameters jointly, i.e. within the same trajectory, with a single Metropolis-Hastings step, using the "advanced hybrid Monte Carlo" algorithm of Beskos et al., 2015 (section 3.2 and algorithm 3): standard HMC dynamics for $\boldsymbol{\theta}$, and diffusion-pathspace dynamics for $\mathbf{u}$.

Each step is a kick-flow-kick Strang splitting (Beskos et al., 2015, equations 14-16): a half kick of both momenta, a flow (the leapfrog drift for $\boldsymbol{\theta}$, an exact rotation for each nuisance parameter), then a second half kick. Hence, each step needs a single evaluation of the gradient of $\log \pi$, as for the leapfrog integrator.

By default, NicoStan makes two changes to the Gaussian reference of Beskos et al., neither of which changes the target (they only change how the Hamiltonian is split): (i) the reference is centred at a running estimate of the posterior mean of $\mathbf{u}$, made during burn-in and frozen before the sampling phase, rather than at $\mathbf{0}$; and (ii) each nuisance parameter has its own mass, estimated during burn-in, so that each rotates with its own frequency.

Note that Beskos et al. use unit masses for the nuisance parameters, which, as they show, makes their algorithm well-posed as the number of nuisance parameters goes to infinity (Beskos et al., 2015, remark 2 and section 3.3); our per-coordinate masses do not necessarily keep this property.

Alenlöv et al., 2021 later used the same split of the Hamiltonian in their pseudo-marginal HMC algorithm, but with the order of the operators reversed (flow-kick-flow, their equation 19); NicoStan uses the kick-flow-kick order of Beskos et al. Other dimension-robust HMC-type algorithms include that of Pinski, 2021 and the manifold MCMC method of Beskos, 2014.

In NicoStan, the nuisance blocks of a Stan model are named with nuisance_params when the model is set up, and diffusion-pathspace HMC is switched on with diffusion_HMC = TRUE (with diffusion_HMC_integrator = "kick_flow_kick") in $sample(); when diffusion_HMC is not given, NicoStan warns and samples the nuisance block with standard HMC. With the standard leapfrog drift for the nuisance parameters instead of the rotation, the sampler is standard HMC for both blocks; the NicoStan paper compares both (*NicoStan: between-chain adaptive hybrid diffusion-pathspace HMC for general Stan models*, in preparation).

Why some of these models are particularly difficult to sample

The MVP and its latent class / ordinal extensions (LC-MVP, LC-MVOP, etc.) are particularly demanding examples. The augmented latent data can be very large, whilst strong correlations and outcome-dependent truncation create difficult dependencies between the latent variables and the model parameters. Additionally, specifically for latent class models, poor identifiability can make sampling harder still (see Talhouk et al., 2012 and Cerullo et al., 2025).

Stochastic volatility and non-linear state-space models can also be difficult when the latent processes are highly persistent or their innovation scales are small.

In frailty survival models, joint longitudinal-survival models and latent-factor models, limited information about the individual effects can induce strong posterior dependence between those effects and their population-level parameters. Techniques such as non-centring can help with these dependencies in some models; however, the remaining high-dimensional latent block can nevertheless make the computation prohibitively expensive.

GPU acceleration and serial dependencies

Some of these models contain calculations that are done in sequence, which limits how much of them can run in parallel (e.g. on a GPU). E.g., in the GHK implementations of the MVP / LC-MVP, the conditional bounds and latent-variable transformations of each outcome depend on the preceding outcomes of the same individual, so they are built up one outcome after another. Similarly, the non-centred reconstruction of a latent path (e.g. the AR(1) log-volatility path of stochastic volatility) needs each state before the next state can be calculated. These dependencies limit the parallelism within an individual / path, although independent individuals, paths and chains can still be processed in parallel.

GPU suitability therefore depends on the model and on the amount of parallel work available: e.g., Stan's OpenCL support is expected to give its largest speed-ups with Stan's specialised GLM functions (e.g. bernoulli_logit_glm).

NicoStan runs on the CPU, and needs no changes to the model for GPU execution. Its hybrid diffusion-pathspace HMC, its between-chain adaptation and its CPU parallelism (many chains, with nico_reduce_sum within each chain) address the cost of posterior sampling directly; the optional AVX2 / AVX-512 functions additionally speed up the evaluation of the log density and its gradient.

nico_reduce_sum and nico_map_rect

Stan's `reduce_sum` splits a sum (e.g., the log likelihood) into chunks, each evaluated on its own autodiff tape, in parallel with oneTBB; this is the basis of tape chunking (i.e., chunks small enough that each one's tape fits in the CPU's caches; see *Cache-aware chunking dramatically improves parallel scaling for HMC: Application to multivariate probit model*, in preparation).

However, with Stan's reduce_sum, some of the work still happens outside the chunks, on the main tape. For a nuisance block with one or more values per unit (e.g., per individual, group or time point), the main tape still holds one node per value, and reduce_sum copies each chunk's slice of the block. Its bookkeeping (the list of the addresses of the sliced argument's nodes, the zeroing of their partial derivatives, and adding each chunk's partial derivatives back into them) also runs over every value of the block, on one thread. These passes over the whole block grow with N, and at large N they no longer fit in the caches.

nico_reduce_sum moves this work inside the chunks:

  • Chunk-local bookkeeping: the bookkeeping of the sliced argument (the addresses, the zeroing and the adding back) is done inside each chunk, for that chunk's slice only.
  • Nuisance blocks held by NicoStan inside the chunks: the nuisance blocks named in nuisance_params are taken out of the Stan parameters and held by NicoStan in one array; each chunk reads only its own slice of the block, whose values become nodes of the chunk's own tape only, and the chunk's nuisance derivatives are added straight into NicoStan's array of the gradient, so that the main tape holds no node per nuisance value.

nico_map_rect is the counterpart of Stan's `map_rect`, for models whose jobs must each return a vector (rather than one sum). Stan's map_rect keeps every job's inputs and their Jacobian on the main tape, so that a nuisance block read by the jobs is first gathered into job arguments on the main tape; nico_map_rect reads the nuisance values of each job inside that job, on the job's own nested tape, instead (see Map jobs in a shared-frailty Cox model).

Map jobs in a shared-frailty Cox model

nico_reduce_sum applies a partial-sum function to slices and returns their sum; nico_map_rect applies a job function and returns a vector of job results. In this Cox model, the observations are sorted by decreasing survival time and split into blocks. Each map job calculates the log-sum-exp of eta within one block, giving that block's log risk. A cumulative log-sum-exp scan of the block results then gives each later block its risk-set offset.

The scalar reducer uses each block's offset to calculate its Cox partial-likelihood contribution and the prior contribution of that block's frailty groups. In other words, the map jobs produce the blocks' risk summaries, and the reducer sums the blocks' contributions. With nico_map_rect, the C++ that NicoStan generates reads the nuisance values needed by each map job inside that job, rather than first gathering the nuisance values of all blocks into job-argument vectors on the main tape.

What it changes inside Stan's autodiff system

nico_reduce_sum directly modifies Stan's internal automatic differentiation (autodiff) system, i.e., the part of the Stan math library that computes the gradient of the log density (Carpenter et al., 2015), rather than only the Stan model. Stan uses reverse-mode autodiff (Margossian, 2019): each operation in the model is recorded as a node (a vari) on a tape (i.e., a list of every operation, in the order in which it was evaluated, kept in Stan's own block of memory, the "arena"). The gradient is then computed by one sweep backwards over the tape, in which each node passes its adjoint (i.e., the derivative of the log density with respect to that node's value) back to the nodes it was computed from.

More specifically, for a model with nuisance blocks NicoStan changes these parts of this system:

  • Stan math's reduce_sum (the C++ header file stan/math/rev/functor/reduce_sum.hpp): the bookkeeping of the sliced argument (the list of its nodes' addresses, the zeroing of their partial derivatives, and adding each chunk's partial derivatives back into its nodes) is done by each chunk, for its own slice only; furthermore, for a nuisance block held by NicoStan, each chunk makes the nodes of its own nuisance values on its own tape (from NicoStan's array of values), and their derivatives are added into NicoStan's array of the gradient, so that the main tape holds no node per nuisance value.
  • Stan math's map_rect (stan/math/rev/functor/map_rect_concurrent.hpp), for nico_map_rect: each job reads its own nuisance values on its own nested tape.
  • BridgeStan's gradient call (BridgeStan's src/model_rng.cpp and src/bridgestan.cpp), so that the gradient of the nuisance block is returned from NicoStan's array, without extra copies.

On Linux, every NicoStan model is also compiled with a change to Stan math's arena (stan/math/memory/stack_alloc.hpp), which lets NicoStan release the memory of each thread's tape after its sampling call.

The gradient is the same as that of the original model, up to the order of a few floating-point additions; we checked this for the stochastic volatility, hierarchical logistic regression, joint longitudinal and survival, population pharmacokinetic and IRT models (96 cases per model; largest relative difference 4.9e-16; see *NicoStan: between-chain adaptive hybrid diffusion-pathspace HMC for general Stan models*, in preparation).

Why it does not change your own Stan, BridgeStan or cmdstanr installation

None of these changes are made to your own installation of Stan. Stan's C++ code is "header-only" for the most part, i.e., it is not a library installed once and shared by every model, but source code that is compiled into each model's own library (the .so file) when that model is built; hence a change to Stan's code only affects the models that are compiled with the changed copy of it.

NicoStan therefore makes its own private copy of your BridgeStan installation (which contains its own copy of the Stan math library), in R's cache folder for NicoStan (tools::R_user_dir("NicoStan", "cache")), makes its changes to that copy only, and points BridgeStan at the copy only whilst it compiles a NicoStan model, then points it back at your own installation straight away. In other words:

  • your own BridgeStan folder is only read (to be copied), never written;
  • CmdStan (which cmdstanr and CmdStanPy use, and which has its own separate copy of the Stan math library) and rstan are never written by NicoStan at all;
  • any model you compile with cmdstanr, rstan or BridgeStan itself is compiled against its own, original copy of Stan, exactly as before.

Note that each change is only made when the lines of the copied file are exactly those NicoStan expects; otherwise NicoStan stops with an error, rather than changing a file which differs from the one it expects (e.g., one from a newer version of Stan). Each private copy is named after the path of the original BridgeStan installation, its arena file and the content of NicoStan's changes, so that a new version of either makes a new copy (rather than reusing an old one); deleting the cache folder removes every copy, and NicoStan simply makes a new one the next time it is needed. These changes are currently made on Linux only.

How to write a model for it

1. Declare each nuisance block in the parameters block, as one of: vector[E], row_vector[E],

array[E] real, array[E] vector[K], array[E] row_vector[K], matrix[R, C] (read whole where it is used), array[A] matrix[R, C], or a tuple of these (each component of a tuple becomes a nuisance block of its own), with E its number of units. Each may have one constraint, <lower = a>, <upper = b>, <lower = a, upper = b>, <offset = a>, <multiplier = b> or <offset = a, multiplier = b>, with bounds that do not use a nuisance block: NicoStan then holds the block's unconstrained values, as Stan's own sampler does, and adds the log-Jacobian of the transform to the target once per value. Any other block (e.g., an array of tuples, or an array of more dimensions) stops with an error saying so. 2. Make the nuisance block the sliced argument of reduce_sum or reduce_sum_static (which may also be written nico_reduce_sum_static), and put everything whose size grows with N (e.g., the nuisance block's prior, the likelihood terms) inside the partial-sum function. Note that reduce_sum slices arrays only, so a vector[E] block should be declared as array[E] real here (otherwise NicoStan stops with an error). A nuisance block that is a shared argument of the partial-sum function is also read inside the chunks. 3. Give the names of the nuisance blocks with nuisance_params (see Example 2).

For instance, for the hierarchical logistic regression (with a random intercept and a random slope for each group, in non-centred form), the nuisance block beta_raw is sliced by groups, and each chunk evaluates the prior of its groups' beta_raw and the likelihood of their observations (the data are sorted by group in transformed data, so that each chunk's observations are contiguous):

functions {
  real partial_sum_groups_lpdf(array[] row_vector beta_raw_slice, int start, int end,
                               vector mu, vector sigma,
                               data array[] int y_sorted, data vector x_sorted,
                               data array[] int group_sorted,
                               data array[] int first_of_group, data array[] int last_of_group) {
    int first = first_of_group[start];
    int last = last_of_group[end];
    matrix[end - start + 1, 2] beta_raw_of_slice = to_matrix(beta_raw_slice);
    matrix[end - start + 1, 2] beta_of_slice;
    for (i in 1:2) {
      beta_of_slice[, i] = mu[i] + sigma[i] * beta_raw_of_slice[, i];
    }
    array[last - first + 1] int position_in_slice
      = to_int(to_array_1d(to_vector(group_sorted[first:last]) - (start - 1)));
    return std_normal_lupdf(to_vector(beta_raw_of_slice))
           + bernoulli_logit_lupmf(y_sorted[first:last] | beta_of_slice[position_in_slice, 1]
                                                          + beta_of_slice[position_in_slice, 2]
                                                            .* x_sorted[first:last]);
  }
}
parameters {
  array[K] row_vector[2] beta_raw;   // the nuisance block (one row per group)
  vector[2] mu;
  vector<lower=0>[2] sigma;
}
model {
  mu ~ normal(0, 2);
  sigma ~ normal(0, 2);
  target += reduce_sum_static(partial_sum_groups_lupdf, beta_raw, groups_per_chunk, mu, sigma,
                              y_sorted, x_sorted, group_sorted, first_of_group, last_of_group);
}

(the full model, with its data and transformed data blocks, is inst/examples/benchmark_models/hierarchical_logistic_regression_chunked.stan), and it is fitted with nuisance_params = c("beta_raw").

NicoStan then writes the nico_reduce_sum version of the model next to it: each nuisance block's declaration is kept as a comment, the reduce_sum call is given the block's term indices as its sliced argument, and a copy of the partial-sum function (named <function>_nicostan_chunked_of_<block>) reads the chunk's own values at its start, under the name of its sliced argument, so that the rest of the function is unchanged. Any other use of a nuisance block (outside reduce_sum) reads its values where it is used; these values are correct, but not chunked.

How NicoStan works

Many Bayesian models have a relatively small number of parameters of direct interest (i.e., the "main" model parameters), but a much larger (i.e., high-dimensional) block of latent variables (or "nuisance parameters"); for instance, models with random effects, stochastic volatility models, and Gaussian process models (see the Models with nuisance parameters section above for more examples). As this nuisance block grows, standard HMC often becomes increasingly expensive.

To address this, NicoStan treats the nuisance parameters (in the unconstrained space) as a change of measure from a Gaussian reference measure (based on Beskos et al., 2011 and Beskos et al., 2013) - i.e., their posterior can be written as a Gaussian reference measure multiplied by a correction term. This formulation is particularly useful when a Gaussian reference captures much of the nuisance-block structure; for instance, a non-centred parameterisation such as x = μ(θ) + L(θ)u, with u ~ N(0, I), gives a standard normal prior for u. The nuisance posterior itself does not need to be Gaussian - its departure from the reference is retained in the correction term.

NicoStan samples the main parameters θ and the latent/nuisance parameters u jointly, within the same hybrid HMC/diffusion-pathspace trajectory:

  • The main model parameters are updated using standard HMC dynamics.
  • For models with nuisance parameters, the nuisance parameters are updated using diffusion-pathspace HMC (Beskos et al., 2013), where the Gaussian part of the dynamics is solved exactly (it is a rotation), so this Gaussian substep adds no integration error, regardless of the size of the nuisance block. The complete trajectory also contains numerical steps for the remaining terms; the Metropolis-Hastings acceptance step corrects their integration error.

Models without a nuisance block (e.g., standard univariate logistic regression) use standard HMC throughout. In our initial tests, we have also found NicoStan to be more efficient than Stan (via cmdstanr) for some of these models; we expect the different burnin/adaptation schemes to contribute to this, although the detailed comparisons are still in progress (see Benchmarks and Efficient burnin algorithms).

The hybrid/joint sampling scheme uses a "kick-flow-kick" splitting (diffusion_HMC_integrator = "kick_flow_kick", the default of $sample()). Its Gaussian-reference dynamics follow Beskos et al., 2011 and the diffusion-pathspace construction of Beskos et al., 2013; Beskos et al., 2015 also describe joint updates of model parameters and latent driving variables. Related approaches include Hilbert-space HMC with Ornstein-Uhlenbeck bridge velocities (Pinski, 2021), and pseudo-marginal HMC (Alenlöv et al., 2021).

NicoStan also has the following two default options:

  • Shifted centre: During burnin, the Gaussian reference is centred at a running estimate of the posterior mean of the nuisance block, which is frozen before sampling (theta_hat_us_rule = "running_mean_frozen"), rather than at zero (theta_hat_us_rule = "zero").
  • Nuisance mass: each nuisance coordinate has its own mass, estimated during burnin (metric_type_nuisance = "Empirical"); alternatively, you can use a single common mass ("uniform_diag") or unit mass ("unit").

Efficient burnin algorithms (SNAPER-HMC and ChEES-R-HMC)

NicoStan's burnin (i.e., warm-up) runs several chains in parallel, and adapts the HMC tuning parameters using information pooled across all of the burnin chains (i.e., between-chain adaptation); whereas Stan normally adapts each NUTS-HMC chain separately.

This between-chain adaptation is based on ChEES-HMC (Hoffman et al., 2021) and SNAPER-HMC (Sountsov and Hoffman, 2022).

More specifically, during burnin, NicoStan adapts:

  • The step size, targeting a mean acceptance probability of adapt_delta (0.80 by default), using an ADAM-type update (Kingma and Ba, 2015); the ADAM moments are reset, and the learning-rate schedule restarted, at the final metric update (eps_adam_reset_at_metric_end and eps_learning_rate_restart_at_metric_end, both TRUE by default), so that the step size settles on the final metric rather than on the acceptance crashes of the earlier metric windows.
  • The mass matrix (i.e., metric) for the main parameters, using either empirical covariance/variance estimates from the burnin chains (metric_type_main = "Empirical", the default) or a numerical Hessian (metric_type_main = "Hessian"); more specifically, the Hessian is computed by finite (central) differences of the main-parameter gradients. Both methods support a diagonal or dense Euclidean metric (metric_shape_main = "diag", the default, or "dense"). With the (default) empirical metric pooled across the burnin chains, NicoStan updates the metric once a metric window holds 8 draws, and rescales the step size and trajectory length at each metric update (i.e., multiplies them by $1/\sqrt{c}$, where $c$ is the geometric mean of the change in the diagonal of the inverse metric; for a dense metric, the geometric mean of the ratios of its eigenvalues); more specifically, a few draws are enough to replace an initial (unit) metric which is far off (e.g., for our ordinal LC-MVOP models), whilst the rescaling means that these early updates do not disturb models whose initial metric is already close (e.g., our binary LC-MVP models). These can be changed via the $sample() arguments pooled_metric_warm_up (a number of draws, 8 by default, or "hard", "soft", "first_window", "n_over_n_plus_k" or "signal_to_noise") and metric_update_rescales_eps_and_tau (TRUE by default). The nuisance masses and centre are adapted separately (see How NicoStan works).
  • The trajectory length, using the criterion selected via burnin_algorithm (see Trajectory-length adaptation algorithms below), also with an ADAM-type update.

The main/nuisance separation means that NicoStan can use a dense empirical or Hessian metric for the main block, whilst retaining a diagonal for a much larger nuisance block (where computing a dense metric would be prohibitively expensive). Stan's standard HMC/NUTS metric interface selects a unit, diagonal or dense metric for the complete unconstrained parameter vector; its dense option therefore includes the nuisance parameters too, rather than exposing separate main/nuisance metric choices. This distinction allows NicoStan to use a dense main-parameter metric without constructing/storing a dense metric for the entire latent/nuisance block.

HMC Trajectory length ($\tau$) adaptation algorithms

Use burnin_algorithm (an argument of $sample()) to choose the trajectory-length adaptation algorithm; the default is "CHESSR" (ChEES-R):

  • "CHESSR" (ChEES-R, the default): The ChEES-rate criterion, using the squared change in the monitored parameters' centred squared radius per realised trajectory length. Proposed by Sountsov and Hoffman, 2022.
  • "SNAPER" (SNAPER): Learns a difficult main-parameter direction, and adapts the trajectory length using squared changes along that direction per unit length. Proposed by Sountsov and Hoffman, 2022.
  • "ChEES" (ChEES): Uses the squared change in the monitored parameters' centred squared radius, without dividing by trajectory length. Proposed by Hoffman et al., 2021.
  • "ESJD" (ESJD rate): Uses the squared jumped distance of the monitored parameters (in the coordinates defined by the current mass matrix) per unit trajectory length, i.e., each trajectory's squared jump divided by its own length. Based on the expected squared jumped distance of Pasarica and Gelman, 2010.
  • "ESJD_CHESSR" (ESJD × ChEES-R), "ESJD_SNAPER" (ESJD × SNAPER), "ESJD_CHESSR_SNAPER" and "ESJD_w50_CHESSR_w25_SNAPER_w25": the geometric means (blends) of the ESJD-rate criterion with ChEES-R and / or SNAPER (see Blended trajectory-length criteria below).

ChEES measures squared changes in the centred squared radius of the parameter vector (Hoffman et al., 2021). ChEES-R (the ChEES-Rate criterion of Sountsov and Hoffman, 2022) divides this change by the trajectory length, so that trajectory length is used as a proxy for computational cost. SNAPER-HMC (Sountsov and Hoffman, 2022) focuses the corresponding criterion along the first principal component (i.e., the direction of largest variance in the coordinates used for adaptation).

The position-based criteria use the main parameters in coordinates defined by the current mass matrix (similarly to Riou-Durand et al., 2023).

We checked NicoStan's SNAPER and ChEES-R implementations against the authors' own JAX implementation (the SNAPER-HMC notebook accompanying Sountsov and Hoffman, 2022) on the German Credit logistic regression of the Inference Gym; more specifically, we compared the minimum (over parameters) ESS of the centred squared draws per gradient evaluation, i.e., the quantity their paper reports. NicoStan's SNAPER agrees with their implementation to within 5%, and their ChEES-R value is reproduced once two differences are accounted for: (i) their implementation divides the ChEES-R and SNAPER criteria by the trajectory length plus one step size (i.e., it charges the extra gradient evaluation of each iteration), which NicoStan offers via the $sample() argument rate_criterion_cost_offset_steps; and (ii) their sampling phase draws the jittered trajectory lengths from a Halton sequence rather than independently, which is worth around 15% ESS per gradient on this model (NicoStan offers this via tau_jitter_sampling_type = "halton"; see below). Note that on our latent-class benchmarks the first of these makes the adapted trajectories longer and the ESS per gradient lower; hence, NicoStan divides by the trajectory length alone by default.

The default trajectory-length settings differ between burnin and sampling:

  • Burnin: randomised trajectory length by default (randomize_tau_burnin = TRUE), drawn as in the sampling phase; setting randomize_tau_burnin = FALSE instead fixes the trajectory length for each burnin iteration at the current tuning setting, which saves burnin time compared to using a randomised $\tau$.
  • Post-burnin (sampling phase): randomised trajectory length (randomize_tau_sampling = TRUE) - drawn uniformly between zero and twice the adapted scale (i.e., $\tau \sim \text{uniform}(0, 2 \bar\tau)$) - with at least one integration step ($L \ge 1$). By default, these lengths are drawn independently (tau_jitter_sampling_type = "uniform"); alternatively, tau_jitter_sampling_type = "halton" takes them from a Halton (base-2 van der Corput) sequence over the same range, as in the SNAPER-HMC authors' implementation. In our testing, this gave about 10% more ESS of the posterior SD per gradient on the German Credit regression, and no measurable change on our binary LC-MVP models.

Note that manual_tau separately controls whether the trajectory length is adapted at all - you can instead set $\tau$ manually, by specifying manual_tau = TRUE, and its fixed value by specifying tau_if_manual (e.g., tau_if_manual = 3.0 to fix $\tau = 3$).

Blended trajectory-length criteria (geometric means of ESJD, ChEES-R and SNAPER)

NicoStan also offers four blended criteria, which are geometric means of the ESJD-rate criterion and the ChEES-R and / or SNAPER criteria. They are described in more detail in *NicoStan: between-chain adaptive hybrid diffusion-pathspace HMC for general Stan models* (in preparation).

The three criteria they blend. Each criterion uses the main parameters in the coordinates defined by the current mass matrix, $z = B(\theta - m)$, where $B$ is the (upper-triangular) Cholesky factor of the metric (i.e., $B^\top B = M$) and $m$ is the running estimate of the posterior mean; $\tau^{(i)}$ is the (jittered) trajectory length of iteration $i$:

  • ESJD rate ("ESJD"): the expected squared jump of $z$ itself, per unit trajectory length, $C_{ESJD} = \mathbb{E}\left[ \lVert z^{(i+1)} - z^{(i)} \rVert_2^2 / \tau^{(i)} \right]$.
  • ChEES-R ("CHESSR"; Sountsov and Hoffman, 2022): the expected squared change in the ChEES function, $\varphi_{ChEES} = \tfrac{1}{2} \lVert z \rVert_2^2$ (Hoffman et al., 2021), per unit trajectory length, $C_{ChEESR} = \mathbb{E}\left[ \left( \varphi_{ChEES}(\theta^{(i+1)}) - \varphi_{ChEES}(\theta^{(i)}) \right)^2 \right] / \tau$.
  • SNAPER ("SNAPER"; Sountsov and Hoffman, 2022): the same along the learned first principal component $v$, with $\varphi_{SNAPER} = (v^\top z)^2$, $C_{SNAPER} = \mathbb{E}\left[ \left( \varphi_{SNAPER}(\theta^{(i+1)}) - \varphi_{SNAPER}(\theta^{(i)}) \right)^2 \right] / \tau$.

Why a geometric mean. Maximising a geometric mean is equivalent to maximising the average of the logarithms of the criteria; in other words, each criterion contributes equally (or with its stated weight) to the choice of $\tau$, regardless of its scale. ESJD measures the jumps of the parameters themselves (a first-moment, i.e., linear, statistic), whereas ChEES-R and SNAPER measure the changes of squared (quadratic) statistics, which are closer to the ESS of the posterior SD; hence, a blend asks the trajectory length to serve both. In our preliminary pilot runs on the latent class models of BayesMVP (see below), ESJD chose shorter trajectories than ChEES-R and SNAPER in all 4 cells, and the blends' trajectory lengths lay between (or at) those of their two components in 7 of the 8 comparisons (e.g., for the binary LC-MVP with $N = 10{,}000$ and a 125-iteration burnin: $\tau = 1.51$ for ESJD, 1.81 for ESJD × ChEES-R, 1.77 for ESJD × SNAPER, 2.43 for ChEES-R and 2.50 for SNAPER). Note that this is not a property of ESJD on every target: for a unit Gaussian with exact dynamics, the ESJD rate is maximised at a longer (fixed) trajectory length than ChEES-R ($t = 2.33$ vs. $1.17$), since the squared radius oscillates twice as fast as the position.

Custom AVX2 and AVX-512 functions

NicoStan can also use our custom C++, vectorised (i.e., SIMD) mathematical functions, which are supplied by NicoSIMD, the SIMD library of both NicoStan and BayesMVP. These include, for instance, exponentials (nico_exp()), logarithms (nico_log()), and normal distribution functions (nico_Phi(), nico_inv_Phi(), nico_Phi_approx() and nico_inv_Phi_approx()), as well as their derivatives, log densities, GLMs and fused likelihood functions.

  • AVX2: four double-precision values per vector operation; supported by most x86-64 CPUs.
  • AVX-512: eight double-precision values per vector operation, on supported processors.
  • General Stan models: declare and call the nico_ functions in the .stan model, then supply their C++ header via Stan_cpp_user_header (NicoSIMD::fn_include_folder_Stan_user_header_and_build_arguments_of_NicoSIMD_for_this_CPU() gives the header and the build arguments for the CPU in use, see Example 3).
  • Specialised BayesMVP models: the same NicoSIMD functions are used within the native implementations.

Note that the AVX versions are not a drop-in switch for an existing Stan model; more specifically, the user has to re-write their Stan model (i.e., the .stan file), so that it calls the nico_ functions of NicoSIMD in place of the Stan::math ones.

The comparison examples (whose Stan models have already been re-written in this way) support separate math_backend = "Stan", "AVX2" and "AVX512" options. NicoSIMD: the SIMD functions on every device

SIMD (single instruction, multiple data) instructions apply one operation (for instance, an addition, a multiplication, or one step of the polynomial approximation of exp()) to several numbers at once, all held in one wide register of the CPU. Which SIMD instructions are available depends on the CPU's instruction set; more specifically:

  • AVX2 (Advanced Vector Extensions 2; 256-bit registers, i.e., four double-precision values per instruction) is an x86 (Intel and AMD) instruction set. It is supported by every Intel Core CPU since the 4th-generation Core CPUs ("Haswell"), and by every AMD CPU since "Excavator", including every AMD Ryzen, Threadripper and EPYC CPU; note that some low-power Intel CPUs (e.g., older Atom, Celeron and Pentium models) do not support it.
  • AVX-512 (512-bit registers, i.e., eight double-precision values per instruction) is also an x86 instruction set. It is supported by AMD's Zen 4 and Zen 5 CPUs (e.g., Ryzen 7000 and 9000, and EPYC 9004 and 9005), by Intel's Xeon (server) CPUs since Skylake-SP, and by some 10th- and 11th-generation Intel laptop and desktop CPUs; however, it is switched off in Intel's 12th-generation (and later) consumer CPUs.
  • NEON (also called Advanced SIMD; 128-bit registers, i.e., two double-precision values per instruction) is the SIMD instruction set of ARM CPUs, which have no AVX. It is supported by every 64-bit ARM CPU, for instance: Apple Silicon (M1-M4) Macs, Qualcomm Snapdragon CPUs (including the Snapdragon X CPUs of Windows on ARM laptops), the Raspberry Pi 3, 4 and 5 (with a 64-bit operating system), and ARM servers such as AWS Graviton, NVIDIA Grace and Ampere Altra.

Mathematical backend and reverse-mode fusion

A fused function combines two or more expensive mathematical operations internally in C++ into one autodiff operation with a combined reverse pass, instead of recording those expensive operations separately on the AD tape. This must happen at the C++ stan::math::var / reverse-mode AD level.

Cheap operations - sqrt, pow, multiplication, division, addition and subtraction - do not count towards the two-operation requirement. Squares and matrix products remain cheap as well.

A wrapper around separate AD calls is not fusion. Computing log1p(exp(x)) inside a C++ function does not qualify when exp and log1p still create separate AD operations. Computing their values internally and registering one operation with combined derivative propagation does qualify.

NicoSIMD also includes SIMDe, for NEON on ARM CPUs (see below). Every SIMD local variable is declared aligned (ALIGN32 for AVX2 and ALIGN64 for AVX-512), so that the AVX code is also safe on Windows. Note that a model compiled without NicoSIMD's functions runs on the Stan::math functions, just more slowly.

Since every model is compiled on the user's own computer, the instruction set is chosen when the model is compiled, based on what the CPU supports (i.e., there is no run-time dispatch: the compiled model contains one set of SIMD functions only). More specifically, NicoSIMD::fn_include_folder_Stan_user_header_and_build_arguments_of_NicoSIMD_for_this_CPU() reads the CPU's instruction sets (from /proc/cpuinfo on Linux; otherwise, e.g., on Windows and macOS, from the macros which R's own C++ compiler defines with -march=native, i.e., the flag each model is compiled with), and chooses one of these four options:

Some more detail on each option:

  • AVX-512 requires three of its extensions: AVX-512F (the foundation), AVX-512VL (the 512-bit instructions also on 256-bit registers) and AVX-512DQ (e.g., the conversions between 64-bit integers and doubles, which the exp() and log() kernels use). Note that Intel switched AVX-512 off in its 12th-generation (Alder Lake) and later consumer CPUs, since their efficiency cores do not support it; it is expected to return in future Intel desktop CPUs, through AVX10. Furthermore, Zen 4 CPUs run each 512-bit instruction as two 256-bit halves; nevertheless, on our Zen 4 server, the AVX-512 versions were at least as fast as the AVX2 versions in almost every case.
  • AVX2 always comes with FMA3 (fused multiply-add, i.e., a * b + c in one instruction, with one rounding), which the polynomial approximations of the kernels (e.g., of exp(), log() and Phi()) use at every step.
  • NEON (through SIMDe): SIMDe ("SIMD Everywhere"; header-only, MIT licence, included in NicoSIMD) implements each x86 intrinsic with the target CPU's own instructions. With SIMDE_ENABLE_NATIVE_ALIASES, the kernels' own intrinsics (e.g., _mm256_fmadd_pd) and types (__m256d) refer to SIMDe's versions, so that the AVX2 kernels compile unchanged on ARM CPUs; since a NEON register holds two doubles (vs. four for AVX2), each 256-bit AVX2 instruction becomes two 128-bit NEON instructions (e.g., _mm256_fmadd_pd becomes two vfmaq_f64). This is close to hand-written NEON code for the arithmetic, although a few AVX2 instructions without a single NEON equivalent (e.g., the gathers) take several NEON instructions. Note that NicoSIMD does not use the scalable vector extensions (SVE / SVE2) of some ARM server CPUs.
  • Stan::math: the model is compiled with Stan's own math library (i.e., exactly as Stan compiles it), whose linear algebra uses Eigen; Eigen itself vectorises its matrix and vector operations with whatever SIMD instructions the compiler enables (e.g., SSE2, AVX or NEON), but the elementwise transcendental functions (e.g., exp(), log() and Phi()) and the log densities are Stan's own scalar versions.

In every case, a compiled model reports the vector width of its NicoSIMD functions through bmvp_simd_lanes() (declared in Stan as real bmvp_simd_lanes();; i.e., 8 for AVX-512, and 4 for AVX2 and for NEON through SIMDe, since SIMDe keeps the AVX2 kernels' width), so that one can check which version is being used.

To check which of these your CPU supports: on Linux, grep -o -w -E 'avx2|avx512f|asimd' /proc/cpuinfo | sort -u (where asimd means NEON, on ARM CPUs); on Windows, a tool such as CPU-Z; on an Intel Mac, sysctl -a | grep machdep.cpu (every Apple Silicon Mac supports NEON, and none supports AVX).
